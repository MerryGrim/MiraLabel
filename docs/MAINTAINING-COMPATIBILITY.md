# Проверка и публикация отчётов о печати

Источником сайта служит только `data/compatibility.json`. GitHub Issues — очередь сообщений, а не автоматически подтверждённая совместимость. Сайт не использует токены, не обращается к API Issues, не принимает загрузки и не отправляет отчёты за пользователя.

## Путь отчёта

На отдельной странице `compatibility.html` доступны все 89 моделей из каталога локального APK NIIMBOT 6.6.9. Данные идентификации находятся в `data/models.json`, их хэши источника — в `source`. Этот список не является набором готовых профилей печати. В нём не публикуются предположительные размеры бумаги или DPI. Числовые коды могут совпадать у разных моделей: это коды каталога, а не подтверждённый ID подключённого устройства.

Поиск учитывает название, пробелы, дефисы, подчёркивания и коды каталога. Кнопка модели открывает форму на выбранном языке с названием и кодами. Для неизвестной модели не подставляется тест D11H, его QR или бумага. Можно описать ошибку подключения или отсутствие попытки печати. Не просите запускать модель через неподходящий профиль. Необязательные поля `model`, `test-spec` и `qr-payload` не требуют повторять сведения из JSON приложения.

Ручные отчёты о других моделях остаются в очереди Issues. Добавление в каталог само по себе не включает печать и не создаёт запись в `reports`. Для публичной записи по новой методике или бумаге сначала требуется описать эту методику и обновить валидатор, сохранив точные фактические условия. На главной странице остаётся компактный переход к каталогу; подробные отчёты по версиям размещены под каталогом в раскрывающемся разделе.

1. Пользователь запускает в приложении проверку **одной** этикетки 12 × 40 мм с зазором. `miralabel-print-check-v1` содержит фиксированный QR `MIRA-D11H-TEST`.
2. Приложение сохраняет безопасный снимок метаданных попытки. Три человеческих ответа независимы от ответа протокола: целая этикетка, текст без обрезки, QR с точным содержимым. Разрешены «нет» и «не проверено».
3. Пользователь открывает форму `report-ru.yml`, `report-en.yml` или `report-zh.yml`, проверяет данные, отдельно соглашается на публичность и сам отправляет Issue. Канонический ID текстового поля — `report`. Приложение может заполнить его через URL; согласие никогда не заполняется автоматически.
4. `compatibility-report` и `needs-review` обозначают очередь проверки. Метки, открытие или закрытие Issue не меняют данные сайта.
5. MerryGrim вручную проверяет сообщение, затем отдельным коммитом или PR добавляет запись в реестр. Автоматический процесс только проверяет данные и тесты; он не объединяет PR и не публикует чужие сведения.

Ручное сообщение без JSON тоже можно отправить. Если точной версии, даты, прошивки, размеров или наблюдений не хватает, задайте вопрос в Issue. Не придумывайте отсутствующие значения ради заполнения реестра. До получения записи, соответствующей методике и схеме, оставьте Issue в очереди, без счётчиков и статуса на сайте. Другие размеры, USB или другая методика требуют отдельного описанного теста и изменения валидатора; их нельзя незаметно записать как этот BLE-тест.

## Что проверить вручную

- Issue публично открывается по `https://github.com/MerryGrim/MiraLabel/issues/N`. Проверьте реального автора по GitHub, а не по тексту сообщения. Несколько Issues одного человека не считаются независимыми участниками.
- В JSON нет серийного номера, BLE/MAC-адреса, рекламируемого имени устройства, имени компьютера, пути, содержимого личной этикетки или сырого журнала. Используются только ограниченные поля экспорта приложения. Для D11H модель по ID — `528`, каноническое имя — `D11_H`.
- `reportId` уникален. Точное приложение, прошивка, версия протокола, BLE, бумага 12 × 40 мм / gap и плотность сохранены. Дата — дата записи теста, не выдуманная дата проверки. Версию или прошивку не заменяют диапазоном «все».
- Наблюдения согласованы. `userResult` пересчитывается валидатором: любой `no` после попытки даёт `reported_failure`, все `yes` дают `reported_success`, часть `yes` и остальные `not_checked` — `reported_partial`, отсутствие наблюдений — `not_checked`. До запуска (`not_run`) физические наблюдения и счётчик страниц не допускаются.
- Даже после ошибки связи этикетка могла выйти. Успех, сообщённый человеком после отсутствующего ACK, сохраняется с `attemptStatus: "error"`; попытка не образует отдельную группу и не скрывает ошибку от похожих успешных отчётов.
- Фото необязательно для обычного сообщения. Если оно есть, оно должно показывать только тестовую этикетку. В `evidenceUrls` допускаются ссылка на исходное Issue и публичные `https://github.com/user-attachments/assets/<UUID>`.

## Уровни доказательств

Каждая запись обязана явно содержать `evidenceLevel`:

- `user_report`: автор проверил содержание сообщения пользователя. Это не означает, что автор сам повторил тест.
- `maintainer_reproduced`: MerryGrim **сам физически повторил** этот тест в указанной конфигурации, опубликовал собственный отчёт и указал публичное подтверждение в `evidenceUrls`. Проверяющий и автор записи должны быть MerryGrim; одного `reviewedBy` для этого статуса недостаточно. Повторный тест тоже может закончиться ошибкой или частичным результатом — это не превращается в успех.

Оба уровня относятся только к указанной конфигурации. Сайт отдельно показывает человеческий исход и уровень доказательств. Никакой уровень не выдаёт общую сертификацию модели или всех прошивок.

По явному подтверждению владельца D11H имеет отметку модели **«Проверено автором»** (`profiles[].ownerStatus: "verified"`). Известная конфигурация физической печати — 0.1.1 / D11H / FW 4.28, BLE; дата теста не зафиксирована. Эта отметка не входит в `reports`, не увеличивает счётчики, не становится повторной проверкой 0.2.7 и не скрывает последующие ошибки или смешанные результаты. Отметка модели и публичные отчёты по точным конфигурациям показаны отдельно.

## Формат записи

Добавьте в `reports` объект с ключами:

```text
issueUrl       — публичное исходное Issue этого репозитория
author         — проверенный GitHub-логин автора Issue
evidenceLevel  — user_report либо maintainer_reproduced
reviewedBy     — MerryGrim
reviewedAt     — YYYY-MM-DD, не раньше даты записи теста
evidenceUrls   — [] либо разрешённые публичные подтверждения
report         — неизменённый безопасный JSON экспорта приложения, schemaVersion 1
```

Дополнительные поля, включая произвольное `confirmed: true`, запрещены. Не вставляйте Markdown, HTML или свободный комментарий внутрь структурированного JSON. При необходимости объяснение остаётся в исходном публичном Issue. Разрешённый проверяющий пока только MerryGrim; расширение списка требует отдельного изменения кода и проверки владельцем.

Обновите `updatedAt` в реестре датой изменения. Оставьте отрицательные и частичные записи. Исправление действительно ошибочного или отозванного сообщения делайте явным коммитом с объяснением и ссылкой на Issue; не удаляйте проблему ради красивой статистики.

## Проверка перед коммитом

Требуется Node.js 20 или новее, зависимости устанавливать не нужно:

```text
node scripts/validate-registry.cjs
node --test tests/registry.test.cjs tests/models.test.cjs
```

Проверяются структура, исходные ссылки, уникальность Issue и ID, проверяющий, явный уровень доказательств, производный результат, единый контракт форм и полнота переводов. Синтетические записи тестов живут только в коде тестов, никогда не в реестре.

Счётчики строятся в браузере из принятых записей. Группа — **ID модели + прошивка + точная версия приложения + BLE + бумага/плотность + testSpec + версия протокола**. `attemptStatus`, ошибки и ACK не разделяют группы. Участники считаются по GitHub-логину без учёта регистра; в каждом исходе один человек учитывается один раз. Один участник может иметь разные исходы, поэтому суммы этих чисел не обязаны совпадать с числом участников. Исходные отчёты остаются доступны под карточкой.

Новый релиз получает новую строку без публичных отчётов. Отметка D11H «Проверено автором» сохраняется как статус модели; старые публичные результаты не переносятся в счётчики нового релиза. Общая строка с неизвестной прошивкой не означает все прошивки и не объединяется с известной 4.28.

Workflow `.github/workflows/validate-registry.yml` запускает только эти проверки с `contents: read`, без secrets, записи в Issues и автоматического merge. Перед merge владелец также проверяет публичные источники и подпись собственного повторного теста вручную. Прохождение CI доказывает согласованность данных, а не физическую печать.
